# MS43 tuning features — design

Date: 2026-10-19. Status: draft, waiting for the user's approval.

Labels: **[user]** = decided by the user; **[call]** = decided by the designer, open to veto;
**[ver]** = checked against the real files on 2026-10-19; **[inf]** = inference to confirm while building.

## 1. Intent

The user tunes their own BMW E46 M54B25 (Siemens MS43 ECU, MS4X custom firmware MS43X001) with
TunerPro and the MS4X XDF, flashes with MS4X Flasher, and logs with this app (`ms43x` ADX). They
want one app that does both: open the car's bin, browse and edit its maps with the right
addresses and scaling, compare two bins, and see live, while logging, where the engine sits on
each map. Logging must keep working as it does today. **[user]**: "yeah pretty much it" to that scope.

## 2. Goals, non-goals, anti-goals

Goals (first version):

1. Open a 512 KiB MS43 bin with a TunerPro XDF; browse every XDF item by category and search.
2. View and edit tables, curves, scalars (constants) and flags in physical units, with undo/redo,
   and save the bin.
3. Curve (2D) and surface (3D) views of tables.
4. Compare two bins item by item (tables, scalars, flags) and report raw bytes that differ outside
   any XDF item.
5. Live cursor: while the logger runs, show the current operating point on the displayed map, and
   show the measured logging refresh rate.
6. Logging keeps every current feature: dashboard, pins, filter, CSV, performance window, CLI.

Non-goals:

- **Checksum verify/fix [user].** MS4X Flasher corrects checksums when flashing. Evidence that
  agrees: both MS43X001 files (the MS4X release and the car's file) carry a stale calibration
  CRC while every other checksum is right and every checksum-bypass switch is stock, and the MS4X
  wiki says a bad checksum blocks engine start. So the car runs only because the flasher rewrote
  it. The algorithm is documented in `../MS43LAB/REPORT.md` §3 if this is ever needed.
- **Live tuning through a RAM overlay [user].** Another session is experimenting with it. Do not
  build hooks for it now.
- Writing to the ECU in any form. The app keeps sending only the ADX-defined logger telegrams.
  Flashing stays in MS4X Flasher.
- Editing program code or applying patches (this XDF has no XDFPATCH entries anyway).
- Finding or naming new maps. The 17 tables found by code analysis that the XDF does not define
  stay out of v1.
- Log replay from CSV files and "time spent per cell" histograms (see §10, later).

Anti-goals (would make it a failure even if it technically works):

- A value shown differently from TunerPro for the same bin and XDF: the same raw bytes must give
  the same physical value, to the digits shown. Cosmetic formatting (digit count on a header,
  hex padding) may differ; §6.2 fixes the rules.
- A saved file whose bytes differ anywhere the user did not edit.
- Losing edits (closing or opening another file without a prompt, crash during save).
- Logging that gets slower or less reliable because of the new features.
- Quick edits that take more clicks than in TunerPro.

## 3. Constraints

- C#/.NET 10, Avalonia 11.3.12, the existing solution layout (`src/MS43Logger.Core`,
  `src/MS43Logger.Cli`, `src/MS43Logger.AvaloniaApp`, `tests/MS43Logger.Core.Tests`, xUnit).
  Windows is the user's platform; keep Avalonia's cross-platform code paths intact.
- Never modify the original bins in `../MS43LAB/bins/` or the user's XDF; tests work on copies or
  read-only.
- The MS4X XDF and ADX are third-party files with no stated licence. **[call]** The XDF is not
  committed; the app loads it from wherever the user keeps it (see §6.3).
- Parse XML safely: refuse DTD/ENTITY declarations (as `../MS43LAB/tools/xdf_import.py` does).
- No new third-party packages unless a part cannot reasonably be drawn with Avalonia itself;
  name and justify any that is added.
- Commit only when the user asks.

## 4. Facts this design rests on [ver]

### 4.1 The MS43X001 XDF matches the car's bin

User's file: `Siemens_MS43_MS43X001_512K.xdf` (TunerPro XDF 1.80, "MS4x Dev Team",
autogenerated, written 2025-10-24; 3,631,992 bytes).

- `BASEOFFSET offset="458752" subtract="0"`: every XDF address is added to 0x70000, so all items
  sit in the calibration area (tables 0x70042–0x7FC20, constants 0x70092–0x73FE0).
- 1,479 tables (616 of them are axis tables in category "Axis"), 2,293 constants, 4 flags,
  no patches, no checksum entries. 64 tables belong to more than one category.
- Cross-check with the table catalogue extracted from the car's bin by code analysis
  (`../MS43LAB/tools/ms43_calmaps.py` run on a copy of the car file with
  `--functions ../MS43LAB/ghidra/out_ms43x/functions.tsv`): 839 tables at the same address with
  the same size and **zero mismatches**; 599 catalogue axes match XDF axis tables (the XDF axis
  address is the first value, after the axis's count byte/word). The XDF also defines the 8 VE
  maps `ip_map_ve_1..8__map__n` (0x7EE20 + n·0x200, 16×16 u16) that code analysis missed.

Encoding found in this file (the parser must handle all of it):

| Element | Values found | Meaning |
|---|---|---|
| `EMBEDDEDDATA mmedtypeflags` | absent, `0x02`, `0x03` | bit 0 signed, bit 1 LSB first (little-endian) |
| `mmedelementsizebits` | 8, 16, 32 | 32 only on label axes and 3 constants |
| `mmedrowcount` / `mmedcolcount` | — | default 1; data is row-major |
| `mmedmajorstridebits` / `minor` | `0/0`, `-32/0` | `-32` only on axes without an address; treat as contiguous |
| axis `embedinfo type="3" linkobjid` | 1,253 links | the axis is another XDF table (category "Axis"); all resolve; addresses and counts agree |
| axis `LABEL index value` | 1,704 axes | fixed labels (curves' single column, enumerations) |
| `MATH equation` | `X`, `k*X`, `k*X+c`, `k * X`, `x`, `50/X`, `(1-(0.0039058823*X-0.5))*Y` | `Y` is `VAR type="link" linkid` → value of a constant (`c_af_stoich_ron98`, `c_af_stoich_e85`) |
| `outputtype` | 1 float, 2 integer, 3 hex, 4 ASCII | display format; `decimalpl` digits |
| `XDFFLAG` | 4 flags on one u16 at 0x707D0 | `mask` selects the bit |
| constant `description` | config switches list `0: … 1: …` | can become a drop-down |

Quirks to tolerate: two pairs of tables share a `uniqueid` (0x2738, 0x7D30; never used as link
targets); one axis has `embedinfo type="3"` without `linkobjid` (`ip_ectpwm_i__tco_dif`, y axis);
one item has no category (`-----Softwareversion-----`); uniqueids also collide across tables
and constants, so links resolve within their kind (axis links → tables, `VAR` links → constants).

### 4.2 Which ECU variable feeds each logged channel

The MS43X001 logger frame (`12 4D A0` + 73 data bytes) is built by `0C:467E`
(`../MS43LAB/ghidra/out_ms43x/decompiled.c`, first function). It copies RAM into the frame buffer
at 0xF750 = data offset 0, and the ADX `packetoffset` counts from the same point (N at 0x04 =
0xF754). Read from the decompiled code; to be confirmed against the disassembly while building [inf]:

| Data offset | Source RAM | ADX channel |
|---|---|---|
| 0x04 | E0E4 & 0x1FFF (rpm); bits 13–15 from 81AC | N; GEAR |
| 0x06 | 847F | VS |
| 0x07 | 84C8 high byte | AMP |
| 0x08 | 8FD6 (manifold pressure) | MAP |
| 0x0A / 0x0B | 8432 / 8433 | TIA / TCO |
| 0x0C / 0x0D | 842F / 8439 | TOIL / TCOEX |
| 0x10 | E31C (VE table index and fraction) | ACTIVEVE |
| 0x12 | E33A (load, fuel) | MAFTI |
| 0x14 | E32C (load, ignition) | MAFIGA |
| 0x16 | E328 (load, VANOS) | MAFIVVT |
| 0x18 | E320 | MAFMMV |
| 0x1A | E330 | MAFMES |
| 0x1C | E32E | MAF |
| 0x2A / 0x2B | E0FE / E15E high bytes | PVS / TPS |

The code catalogue gives, per table, the RAM input of each axis [ver]: part-load ignition maps
0x771D5/0x77315 on E0E4 × E32C, full-load enrichment 0x7D69C/0x7D75C on E33A × E0E4, VANOS maps
0x7629C/0x76390 on E0E4 × E328, many byte maps on 807F × E33B, coolant curves on 8433.
807F is rpm/32 and E33B is the high byte of E33A, so they derive from N and MAFTI [inf].
Inputs the frame does not carry (8450 coolant-at-start, E324, 86FE, the knock copies 83B8/83B7,
8FF6, E00D, and 120 inputs computed in a register just before the call) get no cursor.

## 5. What it looks like

**[user]** "make the UI awesome". The whole app gets one visual identity, the Live tab included
(its features unchanged). A clickable HTML mockup of the Tune tab, built on the car's real
part-load ignition map, is shown to the user before any Tune-tab UI code is written; their

### 5.1 Direction [call]

Subject: one enthusiast tuning their own E46 at a desk or in the car at night. The identity comes
from that car: the E46 instrument cluster (black dials, red-orange backlight, white needles) and
German engineering type (DIN). The map is the instrument; the engine's live position on it is the
one bold, memorable element.

Palette (dark "Night", default):

| Token | Hex | Use |
|---|---|---|
| Dial | `#191C20` | window base |
| Graphite | `#20242A` | panes |
| Bezel | `#2E333A` | 1 px separators, control borders |
| Needle white | `#E8E6E3` | primary text, selection outline |
| Etched grey | `#A3A9B1` | secondary text, axis headers |
| Cluster orange | `#FF6B1A` | **only** "now": live cursor, live readout, connection state, keyboard focus |

Data colours: tables use a cool sequential scale (deep blue `#1B2B3A` → teal `#23707A` → pale
`#F3F6E8`, brighter = higher), so the orange cursor always stands out. Compare deltas use a
diverging blue `#5B8DEF` / coral `#E5675A` pair around the pane colour. Cell text switches dark or
light by contrast. A light "Day" theme mirrors the tokens (pane `#F7F8F9`, text `#1B1F24`, orange
`#D9480F` for contrast).

Type: Bahnschrift, the DIN 1451 family that ships with Windows (no download, fits the subject),
with Inter (already bundled) as the fallback. UI at 13 px; titles 18 px SemiBold; grid numbers in
Bahnschrift SemiCondensed with tabular figures, right-aligned, fixed decimals per item. Sentence
case everywhere: the current ALL-CAPS labels go.

Layout of the Tune tab:

```
┌ MS43 │ Live  Tune  Compare │ car file plate: name, firmware, unsaved count │ port, Connect, 38/s ┐
├──────────────┬─────────────────────────────────────────────┬────────────────────────────────┤
│ search ⌃K    │ ip_iga_ron98_pl__n__maf                      │ 3D surface (drag to rotate)    │
│ categories   │ Target ignition angle for RON98 …   °CRK     │                                │
│  with counts │        load mg/stk →                          │ live: 2 480 rpm, 112 mg/stk,   │
│  items       │  rpm   heatmap grid, live crosshair + trail  │       31.1 °CRK (orange)       │
│              │   ↓                                           │ axes: ldpm_n_14, ldpm_maf_iga_2│
├──────────────┴─────────────────────────────────────────────┴────────────────────────────────┤
│ selection 4×3, min / max / mean │ undo depth │ raw / physical                                 │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

Principles:

1. The map gets the space; chrome recedes into graphite.
2. Orange means "now", and nothing else uses it.
3. Numbers are typeset, not dumped: tabular DIN figures, right-aligned, one decimal count per item.
4. Every change is visible: changed cells carry a mark, the file plate counts unsaved edits.
5. Keyboard-first like a spreadsheet: arrows, Shift to extend, type to set, `+ - *` then Enter,
   Ctrl+Z / Ctrl+Y, Ctrl+K to search.
6. No decoration: panes separated by 1 px bezels, no drop shadows, no card grid, 6 px radius only
   on controls. Motion only in answer to an action (a brief flash on edited cells) and the live
   cursor itself; reduced-motion settings are respected.

The Tune tab otherwise contains: a file plate (bin name, XDF name, firmware ID, unsaved count),
search and category tree with counts and a "modified only" filter, the item editor, and an
inspector with the description, units, axis info ("axis used by N tables") and the 2D/3D view.

## 6. Design

### 6.1 Structure [call]

- Tuning logic goes into `MS43Logger.Core` under a `Tuning` namespace and folder, UI-free, so the
  CLI and tests use it directly: XDF model and parser, bin image with change tracking and undo,
  value codec (raw ↔ physical), firmware identification, comparer, live axis mapping and cursor
  maths.
- `MainWindowViewModel` is split: the polling loop moves into a logger service that publishes
  each decoded sample (values by ADX id plus timestamp) to the Live view, the CSV writer and the
  live cursor. Its behaviour and timing stay as they are.
- Table, curve and surface views are custom-drawn Avalonia controls (a 20×16 heatmap grid with
  selection, cursor and trail does not need a data-grid package).

### 6.2 Reading and writing values

- Element address = XDF address + base offset; file offset = address & 0x7FFFF. Out-of-range
  items are reported and skipped, never read past the image.
- Raw → physical: evaluate the item's equation with `X` = raw value and linked variables (`VAR
  type="link"`) = the linked constant's physical value. Reuse and extend
  `ExpressionEvaluator` (it already has `+ - * / &` and parentheses; make variable names
  case-insensitive for `x`).
- Physical → raw for edits: if the equation is linear in X (check f(0), f(1) and a third point),
  invert it algebraically; otherwise search the raw domain (at most 65,536 values for 8/16 bits;
  bisection for 32 bits, which no editable item here uses). Pick the raw value whose physical value
  is closest, then clamp to the raw range of the element (signed or unsigned).
- Variables: a `VAR` without `type` is the element's own raw value, whatever its id (`X`, `x`,
  and the `X0`/`X00`/`X000`/`X0000` ids used by 19 constants, e.g. `c_t_cp_1` = `0.1*X00`);
  `type="link"` is the linked constant's physical value; any other type is reported as
  unsupported and the item is shown raw and read-only.
- Display rules **[call]**: `decimalpl` digits, 2 when absent (this matches the user's TunerPro
  edit logs, e.g. "changed from 0.00 - (0x80) to 1.00 - (0xA0)"); a linked axis without its own
  `decimalpl` uses the linked axis table's; `outputtype` 2 rounds to the nearest integer
  (`decimalpl` ignored); 3 shows the raw value in hex padded to the element size (`0x0014`);
  4 shows ASCII; absent = 1 (float).
- XDF `min`/`max` and `rangelow`/`rangehigh` are soft limits: warn, don't block.
- Axis tables are editable like any table, with a warning listing the tables that use the axis.
  An edit that makes an axis decrease is refused; one that makes neighbours equal shows a warning,
  since the ECU's search assumes rising breakpoints.

### 6.3 Files

- **Bin**: exactly 524,288 bytes, otherwise refuse. Firmware ID read from the image
  (`ca43X001.DAT` / `ca430069.DAT` at 0x70040, program IDs at 0x6FFB2). Warn when the XDF's `deftitle`
  does not match the bin's firmware (e.g. a 430069 XDF on an MS43X001 bin).
- **XDF**: opened from any path; the app remembers recent XDFs and reopens the last one that
  matched the bin's firmware **[call]**. Stock 430069 bins work through their own XDF (the user
  has `Siemens_MS43_430069_512K.xdf` and `MS430069_512K.xdf`, not checked).
- **Edits and undo**: one undo step per user action (a multi-cell operation is one step); undo
  and redo per open bin; unsaved-changes prompt on close, open and exit.
- **Save [call]**: Save writes the open file. Before the first save of a session it copies the file
  on disk to `<name>.bak` (replacing an older `.bak`). Save As writes elsewhere. The image is
  written in one piece to a temporary file and then moved into place, so a crash cannot leave half
  a file. Nothing but the edited bytes changes, by construction (the image is the file).
- **Edit log [call]**: the user's TunerPro already keeps `<bin name>.log` next to each bin
  ("Edit Log for … created by TunerPro", one line per change, e.g.
  `01/22/2026 22:56:55  Table:     ldpm_n_vim_1 changed.`). On save, append lines in the same
  format to the same file, so one history covers both tools.

### 6.4 Tune tab

- Category tree from `CATEGORYMEM` (an item can appear under several categories), search by name
  and description, filters "modified since opened" and "differs from compare bin".
- Table editor: heatmap colours on physical values, axis headers in physical units, raw/physical
  toggle, cell marker for "changed since opened". Selection with mouse and keyboard.
  Operations on the selection: set value, add, multiply by %, interpolate horizontally /
  vertically / both from the selection's edges, smooth.
- Clipboard **[call]**: copy puts the selection's displayed values on the clipboard as
  tab-separated rows, without axis headers; paste accepts tab-, comma- or space-separated numbers
  and fills the selection (or from the selected cell) when the shape fits, otherwise refuses.
  Whether TunerPro pastes it back the same is a user check (§8), not an automated test.
- Curves (N×1, 1,084 of the 1,479 tables including the 616 axis tables) are shown as a column,
  as TunerPro does, with the 2D chart beside them. Maps: grid plus the 3D surface (mouse
  rotation, reset view). The 3D view is for reading the shape; editing happens in the grid.
- Scalars: value with units; config switches with "0: … 1: …" descriptions get a drop-down.
  Flags: a checkbox per bit.

### 6.5 Compare tab

- Bin A is the working bin; bin B is opened read-only for comparison (the same XDF is used for
  both). The list shows every XDF item that differs: tables with the number of changed cells and
  the largest change in physical units; scalars and flags with A → B.
- Selecting a table shows A, B and B−A grids (B−A as a diverging heatmap). When an axis of the
  table differs between A and B, the view says so at the top, because a cell-by-cell comparison is
  then on different breakpoints (the car's file resampled its rpm axes, which makes about 290
  ignition cells "change").
- "Copy this item from B into A" (undoable), for porting a change between files.
- Bytes that differ outside every XDF item are listed as address ranges with their area name
  (boot block, service sector, program, calibration), so nothing hides. Measured for car vs
  release outside the calibration [ver]: 18 ranges, 11,907 bytes: the boot-block serial, UIF and
  immobilizer bytes (0x3C43–0x3FBB), the 0x8000–0xBFFF service sector (a different factory
  build), and the 26-byte programming signature at 0x4FFE6–0x4FFFF.
- The CLI gets `diff A.bin B.bin --xdf X.xdf` printing the same list **[call]**.

### 6.6 Live cursor and refresh rate

- Mapping chain: XDF table → its data address → the table's axis RAM inputs from the code
  catalogue → the logger channel that carries that RAM variable (§4.2) → the axis raw domain.
  Matching is done on raw values (an axis searched with 807F compares N_raw >> 5; one searched
  with E33B compares MAFTI_raw >> 8), which avoids unit conversions. Physical units are used only
  for display.
- The per-table inputs ship as a generated, committed data file (e.g.
  `definitions/ms43x001_table_inputs.json`) produced from the catalogue CSV, with its provenance
  (tool, commit or hash of the bin, date) in the file. The 8 VE maps are added by hand
  (MAP × rpm per the XDF name and the ADX VE histograms) [inf].
- Cursor: fractional row/column found as the ECU does (clamp at the ends, linear between
  breakpoints), drawn as a crosshair at the fractional position, the four surrounding cells
  outlined by weight, a short fading trail, and the interpolated table value. Tables without a
  mapped input say "no live input" rather than guessing.
- Performance: the cursor reads the latest sample; redraws are throttled (about 30 per second at
  most) and only for the visible item. Nothing new runs on the polling thread.
- Refresh rate: show samples per second (already computed, not shown anywhere today) plus
  interval statistics (average, minimum, maximum in ms over a rolling window) in the Live and Tune
  tabs. This lands first (phase 0) so it measures the unchanged loop.

### 6.7 CLI

Add `show` (print one item, as values and raw) and `diff` (§6.5) next to today's logging options
**[call]**. They exercise the core without the UI and make checks against TunerPro easy.

## 7. Feature order

Each phase ends with its tests passing and a short note of what was and wasn't checked.

0. **Logging baseline**: show the refresh rate (samples per second, which the app computes but no
   view shows today, plus interval statistics) on the unchanged polling loop, so a rate measured
   before the logger refactor exists. CSV rows already carry a UTC timestamp, so an existing car
   log gives the same baseline without a new run.
1. **Core**: XDF parser and model, bin image, value codec, firmware ID, CLI `show`.
   Done when the tests in §8 pass and `show` prints a few tables the user can compare with TunerPro.
2. **Tune tab**: browser, editors, operations, undo/redo, save with backup and edit log.
   Done when the user can edit a copy of the car file and see the same values in TunerPro.
3. **2D and 3D views**.
4. **Compare tab** and CLI `diff`.
5. **Live cursor** and refresh-rate statistics. Done in software when replayed samples move the
   cursor to the expected cells; done for real when the user sees it follow the engine on the car.

## 8. Tests and acceptance

Automated (xUnit):

- Parser on small synthetic XDF strings covering every row of the encoding table in §4.1 and every
  quirk listed under it, plus big-endian and signed elements.
- Real files (copies in a git-ignored `testdata/local/` folder; tests skip when absent):
  - The user's XDF parses to 1,479 tables, 2,293 constants, 4 flags; every axis link resolves
    except the known one.
  - Known car values [ver] (release values in brackets): `c_conf_n_max` = 1 [0],
    `c_conf_lc` = 1 [0], `c_conf_nls` = 1 [0], `c_conf_load` = 1 [1], `c_conf_bc` = 0 [0],
    `c_inj_flow` (u16 at 0x70E14) = 225 [237], `c_lc_n_max` = 141 raw = 4,512 rpm [110],
    `id_n_max_max_mt__gear` first cell = 222 raw = 7,104 rpm [206]; `ldpm_n_11` (0x74B6E) =
    800, 1250, 1750, 2200, 2500, 3000, 3250, 3750, 4096, 4250, 4500, 5000, 5900, 6480, 6980, 6990.
  - Firmware ID strings in the car bin: `ca43X001.DAT` at 0x70040, `43X001` inside the IDs at
    0x6FFB2 and 0x70000.
  - Raw → physical → raw is the identity for every cell of every item in the car bin.
  - Open and save without edits gives identical bytes; one edited cell changes only that cell's
    bytes; undo restores the original bytes.
  - Compare car vs release lists at least the config switches above, 0x70E14, the resampled rpm
    axes, and the expected non-XDF ranges.
  - Live cursor maths on synthetic samples (edges, clamping, u8/u16 axes, derived inputs).
- The existing 8 tests keep passing.

Real-world acceptance (only the user can do these; report them as not done until they are):

- Three or more tables and a few scalars look the same as in TunerPro with the same bin and XDF.
- A file saved by the app opens in TunerPro with the expected values, and MS4X Flasher accepts it.
- On the car: logging still works at the same rate, and the cursor follows rpm and load.

## 9. Decisions marked [call] (for the user to check)

Tabs in the main window; XDF loaded from a user path, not committed; `.bak` before the first save;
TunerPro-format edit log appended to `<bin>.log`; CLI `show` and `diff`; real-file tests skip when
the files are absent; custom-drawn grid/curve/surface controls; raw-domain cursor matching; edits
refused when they make an axis decrease; soft limits from XDF min/max; display rules and clipboard
format (§6.2, §6.4); curves shown as a column; the refresh-rate display first (phase 0).

## 10. Left to the builder, and later

Builder: control internals, view-model layout, colours and scales, keyboard shortcuts (TunerPro-like
where cheap), file naming of the generated input map, how the 3D surface is projected.

Later, not in v1: log replay from CSV with "time spent per cell"; comparing on A's breakpoints
(resample B onto A's axes); axis resampling with re-interpolation of every table using the axis;
the 17 code-only tables; RAM-overlay live tuning (other session).
